## Database migrations

Schema lives in `src/db/schema.ts`; migrations are SQL files in `drizzle/`, generated by Drizzle Kit and committed.

**How they run.** Every Vercel production build runs `scripts/migrate.ts` before `next build` (`vercel-build` in package.json). If a migration fails, the build fails and the live site stays on the previous version. Preview builds skip migrations, because previews share the production database, unless `MIGRATE_PREVIEWS=1` is set (only do that after Neon preview branching is on). Locally: `bun run db:migrate`.

**Changing the schema**

1. Edit `src/db/schema.ts`.
2. `bun run db:generate --name <what_changed>` and read the generated SQL before committing.
3. `bun run db:migrate` locally, then commit `schema.ts` and everything new in `drizzle/` together.
4. CI (`.github/workflows/ci.yml`) fails if the schema and migrations disagree (`bun run db:check`), and runs every migration on an empty database.

**Rules**

- **Backward compatible only (expand → contract).** A migration runs *before* the new code is live, and old code keeps running against the new schema until the switch, and again after a rollback. Every migration must therefore work with the code currently in production:
  - Add columns as nullable or with a default. Add tables freely.
  - Never rename or drop a column/table in the same deploy that stops using it. Deploy 1: add the new thing and write to both. Deploy 2: switch reads. Deploy 3: drop the old thing.
  - Don't add `NOT NULL` to an existing column in one step; add it nullable, backfill, then constrain.
- **Never edit or delete a migration that has been pushed.** Fix forward with a new one. Don't touch `drizzle/meta` by hand, and never use `drizzle-kit push`.
- **Data changes** (backfills, seed-like inserts) go in a custom migration: `bun run db:generate --custom --name <name>`, then write the SQL.
- **Keep migrations small and fast.** Builds run them with `lock_timeout = 10s` and `statement_timeout = 120s`. Create indexes on large tables with `CREATE INDEX CONCURRENTLY` in a migration of its own.
- **Never run migrations against production by hand.** The deploy does it.
